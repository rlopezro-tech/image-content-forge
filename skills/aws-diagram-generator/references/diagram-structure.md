# AWS Service Diagram Structure

Use this structure for every AWS service diagram prompt generated by the `aws-diagram-generator` skill.

## Canvas

- Format: vertical social media infographic.
- Default size: 1080 x 1350 px.
- Alternative size: 1080 x 1920 px for stories, reels, or services that need more vertical space.
- Final export format: PNG.
- Background: white or very light neutral.
- Style: clean AWS-inspired technical infographic.
- Visual density: informative but readable on mobile screens.
- Audience: technical learners, engineers, architects, and cloud practitioners.
- Width rule for every generated card: on a 1080 px wide canvas, use a main content frame about 984-1016 px wide, with the left edge around x=32-48 px and the right edge around x=1032-1048 px.
- This width rule applies to both `Overview` and `Deep Dive` cards.
- Do not compose a narrow centered poster inside the canvas. Avoid 70+ px blank gutters on both sides.
- Header, workflow, and full-width sections should span nearly the full usable width. Two-column or multi-column rows should fill that same usable width with compact internal gutters.

## Required Layout

Every diagram must contain these sections:

1. Header
2. `WHAT IS IT?` panel
3. `HOW IT WORKS` workflow
4. `INTEGRATES WITH` section
5. `BENEFITS` section
6. `COMMON USE CASES` section
7. Source note

## Header

The header must appear at the top.

Include:

- Official AWS service icon when available.
- Official service name.
- Short value proposition.
- One concise description sentence.

Format:

```text
{AWS_SERVICE_NAME}
{SHORT_VALUE_PROPOSITION}
{ONE_SENTENCE_DESCRIPTION}
```

Example:

```text
AWS CodeBuild
Build and test code at scale
A fully managed build service that compiles source code, runs tests, and produces deployable artifacts.
```

## WHAT IS IT?

Place this panel directly below the header.

Requirements:

- Title: `WHAT IS IT?`
- 2-3 concise sentences.
- Explain the service in plain English.
- If the official service name contains an acronym or abbreviation, expand it in the first sentence using the official meaning confirmed by AWS documentation. Example: `Amazon EC2, short for Amazon Elastic Compute Cloud, ...`. Do not guess expansions; if AWS does not document the meaning, omit the expansion.
- Mention managed nature, scaling, pricing model, durability, or availability only when confirmed by official AWS documentation.
- Avoid unsupported superlatives.

## HOW IT WORKS

Place the main workflow in the center.

Requirements:

- Title: `HOW IT WORKS`
- 3-5 numbered steps.
- Directional arrows between steps.
- Each step has a number badge, short title, concise explanation, and relevant visual container.

Recommended pattern:

```text
1. Input / Request / Source
2. Service Configuration
3. Managed Processing
4. Output / Result
5. Monitoring / Access / Automation
```

Adapt the workflow to the service. Do not force the same workflow onto every service.

## INTEGRATES WITH

Place this as a compact section below the main workflow.

Requirements:

- Title: `INTEGRATES WITH`
- 5-7 confirmed AWS integrations.
- Each item includes an AWS icon, service or feature name, and short purpose phrase.

Only include integrations confirmed by official AWS documentation.

## BENEFITS

Place this as a compact section below the integrations section.

Requirements:

- Title: `BENEFITS`
- 4-6 supported benefits.
- Each benefit includes an icon, uppercase heading, and one concise explanation.

Allowed benefit heading examples:

- SCALABLE
- MANAGED
- SECURE
- COST-EFFECTIVE
- FLEXIBLE
- HIGHLY AVAILABLE
- OBSERVABLE
- DURABLE
- INTEGRATED

Only use headings that fit the service and are supported by official AWS documentation.

## COMMON USE CASES

Place this as a compact section near the bottom.

Requirements:

- Title: `COMMON USE CASES`
- 4-6 practical use cases.
- Each item includes an icon and short label.
- Keep labels concise.

## Source Note

Include a small source note at the bottom:

```text
Sources: Official AWS Documentation and AWS Architecture Icons
```

Keep full source URLs in the Markdown prompt file, not inside the diagram image.

## Visual Rules

Use:

- Vertical layout optimized for social media feeds.
- Official AWS Architecture Icons when possible.
- AWS blue, deep navy, purple accents, and service-category colors when useful.
- Thin borders.
- Subtle shadows.
- Clear spacing.
- Tight useful side margins; both `Overview` and `Deep Dive` cards must use the available horizontal space.
- No wide side gutters; side whitespace of 70+ px on both sides is a layout error, not a premium whitespace choice.
- Readable typography on mobile.
- Simple vertical arrows for workflows.
- Consistent section titles.

Avoid:

- Dark backgrounds.
- Blurry or decorative backgrounds.
- Excessive gradients.
- Tiny text.
- Overcrowding.
- Desktop-only wide layouts.
- Generic stock icons when AWS icons are available.
- Claims not confirmed by official AWS docs.

## Markdown Prompt Template

Use this template for each generated service prompt:

```markdown
# {AWS_SERVICE_NAME} Diagram Prompt

## Official AWS Sources

- {SOURCE_1}
- {SOURCE_2}
- {SOURCE_3}

## Image Generation Prompt

Create a vertical AWS educational infographic for {AWS_SERVICE_NAME}.

Final output format: PNG.

Recommended canvas: 1080 x 1350 px.

Use 1080 x 1920 px only if the diagram needs more vertical space.

All visible text must be in English.

Use official AWS Architecture Icons when possible.

### Header

{HEADER_CONTENT}

### WHAT IS IT?

{WHAT_IS_IT_CONTENT}

### HOW IT WORKS

{NUMBERED_WORKFLOW_STEPS}

### INTEGRATES WITH

{CONFIRMED_INTEGRATIONS}

### BENEFITS

{SUPPORTED_BENEFITS}

### COMMON USE CASES

{COMMON_USE_CASES}

### Visual Style

Use a clean AWS-inspired technical infographic style with a white or very light background, thin blue or purple borders, subtle shadows, vertical flow arrows, readable mobile typography, and consistent spacing.

### Source Note

Add a small source note: "Sources: Official AWS Documentation and AWS Architecture Icons".

## Accuracy Checklist

- Service definition is confirmed by official AWS documentation.
- Workflow steps match official AWS documentation.
- Integrations are confirmed by official AWS documentation.
- Benefits are supported by official AWS documentation.
- Use cases are realistic and AWS-aligned.
- All visible text is in English.
- AWS service names use official capitalization.
- Final format is PNG.
- Canvas is vertical and readable on social media feeds.
```
